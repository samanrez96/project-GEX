# استراتژی فرانت‌اند پروژه مدیریت مرکز جراحی

این سند برای مشخص کردن مسیر اجرای فرانت‌اند پروژه، اصلاح باگ‌های فعلی و یکدست‌سازی رفتار صفحات نوشته شده است. هدف این است که پنل مدیریتی فارسی، راست‌چین، ساده، تمیز و قابل استفاده روزمره باشد و با بک‌اند Django REST Framework هماهنگ کار کند.

---

## 1. هدف کلی فرانت‌اند

فرانت‌اند باید یک پنل مدیریتی کامل برای مرکز جراحی باشد که کاربر بتواند از طریق آن این بخش‌ها را مدیریت کند:

- داشبورد اصلی
- دارو و تجهیزات
- تامین‌کننده‌ها و خریدها
- کارمندان
- حقوق و دستمزد
- عمل های جراحی
- امور مالی و تراکنش‌ها
- مخاطبین
- گزارش‌ها

تمام صفحات باید فارسی، راست‌چین و قابل فهم باشند. کاربر نباید برای انجام کارهای ساده مثل اضافه کردن دارو، ویرایش محصول، دیدن تراکنش مالی یا مشاهده حقوق و دستمزد با صفحه خالی یا صفحه اشتباه روبه‌رو شود.

---

## 2. اصول اصلی طراحی و پیاده‌سازی

### 2.1 زبان و جهت صفحه

- کل پنل باید `RTL` باشد.
- تمام متن‌های قابل مشاهده باید فارسی باشند.
- از عبارت‌های دقیق و یکدست استفاده شود.
- عبارت «اعمال جراحی» نباید استفاده شود.
- عنوان درست بخش جراحی‌ها باید دقیقاً این باشد:

```text
عمل های جراحی
```

### 2.2 ساختار صفحات

هر بخش اصلی بهتر است این ساختار را داشته باشد:

1. صفحه لیست
2. صفحه افزودن
3. صفحه ویرایش
4. صفحه جزئیات، در صورت نیاز
5. حالت loading
6. حالت error
7. حالت empty state

هیچ صفحه‌ای نباید بدون پیام، بدون داده و بدون توضیح خالی بماند.

### 2.3 اتصال به API

- همه درخواست‌ها باید از مسیرهای بک‌اند موجود استفاده کنند.
- مسیرهای API زیر `/api/v1/` هستند.
- قبل از ساخت route یا service جدید، فایل‌های route/service فعلی بررسی شوند.
- اگر endpoint دقیق وجود دارد، از همان استفاده شود.
- اگر اسم endpoint بین frontend و backend فرق دارد، frontend باید با endpoint واقعی بک‌اند هماهنگ شود.

### 2.4 مدیریت خطا

برای همه فرم‌ها و درخواست‌ها این حالت‌ها لازم است:

- نمایش loading هنگام دریافت اطلاعات
- نمایش خطای فارسی هنگام شکست درخواست
- نمایش پیام موفقیت بعد از ذخیره
- جلوگیری از submit چندباره
- نمایش validation backend به زبان قابل فهم

## 3. استراتژی کلی کامپوننت‌ها

### 3.1 فرم مشترک محصول

برای محصول، دارو و تجهیزات باید یک فرم مشترک وجود داشته باشد.

این فرم باید در دو حالت کار کند:

- حالت افزودن
- حالت ویرایش

تفاوت این دو حالت:

| حالت | رفتار |
|---|---|
| افزودن | فرم خالی نمایش داده شود و با `POST` ذخیره شود |
| ویرایش | اطلاعات محصول با `GET` دریافت شود، فرم پر شود و با `PATCH` یا `PUT` ذخیره شود |

فرم ویرایش نباید جدا از فرم افزودن ساخته شود. همان فرم باید reusable باشد.

### 3.2 جدول‌های مشترک

لیست‌های اصلی مثل محصولات، کارمندان، خریدها، عمل‌ها، تراکنش‌ها و حقوق و دستمزد باید از یک الگوی مشترک استفاده کنند:

- سرچ
- فیلتر
- pagination
- ستون عملیات
- دکمه مشاهده
- دکمه ویرایش
- empty state

### 3.3 فرم‌ها

تمام فرم‌ها باید:

- label فارسی داشته باشند
- placeholder فارسی داشته باشند
- پیام خطای فارسی داشته باشند
- بعد از ذخیره موفق، کاربر را به صفحه درست برگردانند
- در حالت edit مقدار اولیه داشته باشند

---

## 4. اصلاحات ضروری فعلی

## 4.1 مشکل ویرایش دارو

### مشکل فعلی

وقتی روی ویرایش دارو کلیک می‌شود، فرم اضافه کردن یا فرم قابل ویرایش محصول باز نمی‌شود.

### رفتار درست

وقتی کاربر روی دکمه ویرایش یک دارو کلیک می‌کند:

1. باید وارد فرم محصول در حالت ویرایش شود.
2. اطلاعات همان دارو باید از API گرفته شود.
3. فرم با اطلاعات قبلی پر شود.
4. عنوان صفحه باید مثلاً این باشد:

```text
ویرایش دارو
```

5. دکمه ذخیره باید اطلاعات را آپدیت کند، نه محصول جدید بسازد.
6. بعد از ذخیره موفق، کاربر به لیست محصولات یا صفحه جزئیات همان محصول برگردد.

### راهکار فنی پیشنهادی

- route ویرایش محصول بررسی شود.
- دکمه edit در جدول داروها باید به route درست برود.
- اگر فرم افزودن محصول وجود دارد، همان فرم برای edit هم استفاده شود.
- فرم باید prop یا state مثل `mode = "create" | "edit"` داشته باشد.
- در حالت edit، با `productId` اطلاعات محصول load شود.
- submit در حالت create باید `POST` باشد.
- submit در حالت edit باید `PATCH` یا `PUT` باشد.

### معیار پذیرش

- از لیست داروها روی ویرایش کلیک شود.
- فرم ویرایش باز شود.
- اطلاعات قبلی دارو داخل فرم باشد.
- با ذخیره، همان دارو آپدیت شود.
- رکورد جدید ساخته نشود.

---

## 4.2 مشکل صفحه تراکنش‌های مالی

### مشکل فعلی

در بخش مالی، صفحه تراکنش‌ها به جای نمایش لیست تراکنش‌ها، صفحه تکراری داشبورد اصلی را نمایش می‌دهد.

### رفتار درست

صفحه تراکنش‌های مالی باید یک صفحه مستقل باشد، نه کپی داشبورد.

این صفحه باید موارد زیر را نمایش دهد:

- لیست درآمدها و هزینه‌ها
- نوع تراکنش
- دسته‌بندی
- مبلغ
- تاریخ
- وضعیت پرداخت
- توضیحات
- مرجع مرتبط مثل خرید، حقوق یا عمل جراحی

### راهکار فنی پیشنهادی

- route مربوط به تراکنش‌های مالی بررسی شود.
- اگر route به کامپوننت داشبورد وصل شده، باید به کامپوننت جداگانه `FinanceTransactionsPage` یا معادل موجود وصل شود.
- اگر کامپوننت لیست تراکنش وجود ندارد، ساخته شود.
- کامپوننت داشبورد مالی فقط برای summary و نمودارها استفاده شود.
- صفحه transactions فقط برای جدول تراکنش‌ها استفاده شود.

### ساختار پیشنهادی صفحه

```text
عنوان: تراکنش‌های مالی
فیلترها: نوع تراکنش، دسته‌بندی، بازه تاریخ، وضعیت پرداخت
جدول: تاریخ، نوع، دسته، مبلغ، مرجع، وضعیت، توضیحات، عملیات
```

### معیار پذیرش

- کلیک روی منوی تراکنش‌ها نباید داشبورد اصلی را نشان دهد.
- صفحه باید جدول تراکنش‌ها را نشان دهد.
- اگر داده‌ای وجود ندارد، empty state فارسی نمایش داده شود.

---

## 4.3 مشکل صفحه حقوق و دستمزد

### مشکل فعلی

صفحه حقوق و دستمزد هیچ چیزی نمایش نمی‌دهد.

### رفتار درست

صفحه حقوق و دستمزد باید حتی در حالت بدون داده هم چیزی نمایش دهد.

حداقل خروجی لازم:

- عنوان صفحه
- توضیح کوتاه
- کارت‌های خلاصه
- جدول حقوق و دستمزد یا گزارش payroll
- پیام empty state اگر داده‌ای وجود ندارد
- دکمه افزودن یا تعریف حقوق، اگر در سیستم وجود دارد

### راهکار فنی پیشنهادی

- کامپوننت payroll بررسی شود.
- خطای API در console و network بررسی شود.
- اگر endpoint اشتباه است، با endpoint واقعی backend هماهنگ شود.
- اگر داده خالی است، صفحه نباید سفید بماند.
- اگر permission یا auth مشکل دارد، پیام مناسب نمایش داده شود.

### ساختار پیشنهادی صفحه

```text
عنوان: حقوق و دستمزد
کارت ۱: مجموع حقوق ثابت
کارت ۲: مجموع کمیسیون‌ها
کارت ۳: مجموع پرداختی
جدول: کارمند، نوع حقوق، مبلغ، بازه زمانی، وضعیت، عملیات
```

### معیار پذیرش

- صفحه payroll همیشه render شود.
- در حالت loading پیام مناسب نشان دهد.
- در حالت خطا پیام فارسی نشان دهد.
- در حالت بدون داده empty state نشان دهد.
- در حالت وجود داده، جدول نمایش داده شود.

### رفتار درست

در همه جای فرانت‌اند باید از این عبارت استفاده شود:

## 4.5 اصلاح فرم افزودن محصول

### مشکل فعلی

در فرم افزودن محصول هم «نوع محصول» وجود دارد و هم «دسته‌بندی». کارفرما می‌خواهد فقط نوع محصول انتخاب شود و دسته‌بندی در فرم نباشد.

### رفتار درست

در فرم افزودن محصول فقط این فیلد برای نوع محصول نمایش داده شود:

```text
نوع محصول
```

گزینه‌ها:

```text
دارو
تجهیزات
```

فیلد دسته‌بندی نباید در فرم افزودن محصول نمایش داده شود.

### نکته مهم بک‌اند

قبل از حذف کامل category از payload باید مدل و serializer backend بررسی شود:

- اگر `category` در backend اختیاری است، از فرم و payload حذف شود.
- اگر `category` اجباری است، frontend نباید فیلد را به کاربر نشان دهد، اما باید بر اساس نوع محصول مقدار مناسب را خودکار تعیین کند.
- اگر backend اجازه حذف category را نمی‌دهد و کارفرما category نمی‌خواهد، باید backend هم اصلاح شود.

### رفتار پیشنهادی

- کاربر فقط انتخاب کند: دارو یا تجهیزات.
- اگر backend category لازم دارد، سیستم خودش category پیش‌فرض دارو یا تجهیزات را بفرستد.
- کاربر نباید فیلد دسته‌بندی را ببیند.

### معیار پذیرش

- فرم افزودن محصول فیلد دسته‌بندی نداشته باشد.
- فقط نوع محصول نمایش داده شود.
- محصول با انتخاب دارو یا تجهیزات بدون خطا ساخته شود.
- لیست محصولات همچنان بتواند دارو و تجهیزات را جدا کند.

- هزینه کل

- تب یا فیلتر دارو و تجهیزات

- نمایش قیمت آخر

- دکمه مشاهده جزئیات

## 5.3 امور مالی

بخش مالی باید حداقل دو صفحه جدا داشته باشد:

1. داشبورد مالی

تراکنش‌های مالی برای لیست درآمد و هزینه است.

این دو صفحه نباید یک کامپوننت تکراری داشته باشند.

## 7. پرامپت پیشنهادی برای Claude Code یا برنامه‌نویس

```text
تو یک Frontend Developer حرفه‌ای هستی. پروژه یک پنل مدیریت مرکز جراحی فارسی و راست‌چین است که با بک‌اند Django REST Framework کار می‌کند و APIها زیر مسیر /api/v1/ هستند.

اول ساختار فعلی frontend را کامل بررسی کن. بدون حذف یا بازنویسی غیرضروری، فقط مشکلات زیر را اصلاح کن:

1. وقتی در لیست داروها روی ویرایش کلیک می‌شود، باید همان فرم افزودن محصول در حالت ویرایش باز شود، اطلاعات دارو از API لود شود، فرم پر شود و ذخیره با PATCH یا PUT انجام شود. رکورد جدید نباید ساخته شود.

2. در بخش مالی، صفحه تراکنش‌ها نباید داشبورد اصلی یا داشبورد مالی تکراری را نشان دهد. route مربوط به تراکنش‌ها را به یک صفحه مستقل لیست تراکنش‌ها وصل کن. این صفحه باید جدول درآمدها و هزینه‌ها، فیلترها، loading، error و empty state داشته باشد.

3. صفحه حقوق و دستمزد الان چیزی نمایش نمی‌دهد. علت را بررسی کن: route، component، API call، permission، empty data یا خطای render. صفحه باید همیشه عنوان، summary، جدول یا empty state فارسی نمایش دهد.

4. در کل frontend عبارت «اعمال جراحی» را با «عمل های جراحی» جایگزین کن. این تغییر باید در sidebar، breadcrumb، title، dashboard card، empty state و constants انجام شود.

5. در فرم افزودن محصول، فیلد دسته‌بندی نباید نمایش داده شود. فقط فیلد «نوع محصول» با گزینه‌های «دارو» و «تجهیزات» نمایش داده شود. اگر backend هنوز category لازم دارد، آن را در frontend به صورت hidden/automatic بر اساس نوع محصول مقداردهی کن یا اگر backend اصلاح لازم دارد، دقیق گزارش بده.

محدودیت‌ها:
- طراحی کلی پروژه را خراب نکن.
- استایل RTL فارسی حفظ شود.
- کامپوننت‌های موجود را تا حد امکان reuse کن.
- اسم route ها و API service ها را قبل از تغییر بررسی کن.
- بعد از اصلاح، سناریوهای دستی مربوط به افزودن، ویرایش، تراکنش‌ها، payroll و عنوان عمل های جراحی را تست کن.

خروجی مورد انتظار:
- توضیح کوتاه از فایل‌هایی که تغییر دادی.
- توضیح اینکه هر مشکل از کجا بوده و چطور حل شده.
- لیست تست‌هایی که انجام شده یا باید انجام شود.
```
